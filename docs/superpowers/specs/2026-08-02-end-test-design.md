# end-test — 세션 인지 점검 스킬

작성일: 2026-08-02

## 문제

에이전틱 코딩은 결과물이 돌아가는 것과 사용자가 그것을 이해하는 것을 분리한다.
코드는 늘어나는데 "왜 이렇게 짰는지"는 에이전트 쪽에만 남는다. 사용자는
자신이 어디까지 알고 있고 어디부터 모르는지 알 방법이 없다.

`end-test`는 작업 세션이 끝날 때 그날 다룬 내용을 문제로 되돌려주고, 답변을
채점해서 이해가 빈 곳을 찾아준다.

## 범위

**하는 것**

- 현재 세션의 대화 맥락에서 출제
- 서술형 문답, 한 문제씩 즉시 채점
- 틀린 항목을 로컬 파일에 기록

**안 하는 것**

- 과거 세션 소환 (세션 JSONL 파싱 없음)
- 자동 실행 (훅 없음. 사용자가 직접 호출)
- 약점 통계·추이 분석

과거 세션 복습과 통계는 세션 로그가 충분히 쌓인 뒤에 별도로 판단한다.
지금 넣으면 검증되지 않은 기능에 파서를 붙이는 일이 된다.

## 형태

개인 스킬 하나. `SKILL.md` 마크다운 한 장이며 스크립트도 MCP 서버도 없다.

근거:

- 출제 재료인 세션 맥락을 에이전트가 이미 들고 있다. 파싱할 대상이 없다.
- 출제와 채점은 판단 작업이라 결정론적 코드로 표현되지 않는다.
- 파일 입출력은 에이전트의 Read/Write로 충분하다.

## 호출

```
/end-test        # 5문항
/end-test 3      # 3문항
```

인자는 문항 수 하나뿐이다. 범위·난이도 옵션은 두지 않는다.

## 출제

### 대상 축

세션 내용에서 아래 네 축의 후보를 뽑고, 축이 한쪽으로 쏠리지 않게 섞는다.

1. **설계 판단과 트레이드오프** — 이번 세션에서 실제로 내린 결정의 근거와 비용
2. **장애·엣지케이스 상황판단** — 이 코드가 프로덕션에서 깨진다면 어디서 깨지는가
3. **쓴 기술의 CS 기본기** — 등장한 기술의 근본 원리
4. **그냥 넘어간 지점** — 사용자가 확인 없이 통과시킨 곳

### "그냥 넘어간 지점" 판정 기준

네 번째 축은 판정이 모호하므로 기준을 명시한다. 아래에 해당하면 후보다.

- 에이전트가 설계 선택을 했는데 근거를 설명하지 않고 지나간 곳
- 사용자가 되묻지 않고 승인만 한 변경 (`ㅇㅋ`, `고고`, `ㄱㄱ` 등)
- 에이전트가 도입한 라이브러리·패턴 중 사용자가 한 번도 언급하지 않은 것
- 에러가 났고 에이전트가 고쳤는데 사용자가 원인을 묻지 않은 경우

이 축을 다른 셋보다 우선한다. 도구의 목적에 가장 직접적이기 때문이다.

### 문항 형식

- 서술형. 객관식은 쓰지 않는다. 고르는 것과 설명하는 것은 다른 능력이다.
- 한 문항은 한 개념만 묻는다.
- 세션에서 실제로 나온 코드·결정을 지문에 넣어 추상적 암기 문제가 되지 않게 한다.
- 문항 머리에 축을 표시한다. 예: `Q2/5 · [장애 상황]`

## 진행

한 문제씩 낸다. 사용자가 답하면 즉시 채점하고 다음으로 넘어간다.
문제지를 한꺼번에 주지 않는다.

## 채점

정답 여부가 아니라 **설명할 수 있는가**로 판정한다.

| 판정 | 뜻 | 그 자리에서 | 파일 기록 |
|---|---|---|---|
| ○ | 메커니즘까지 설명함 | 다음 문항 | 없음 |
| △ | 결론은 맞으나 이유가 비었거나 틀림 | 빠진 부분만 짚고 넘어감 | 없음 |
| ✗ | 모름 또는 오개념 | 보충 설명 후 즉시 재질문 | 기록 |

△를 별도 판정으로 두는 이유: "돌아는 가는데 왜인지 모름"이 정확히 △이고,
이 도구가 겨냥하는 상태가 그것이다. ○/✗ 이분법으로는 이 상태가 ○에 흡수된다.

### ✗ 처리

1. 무엇을 놓쳤는지 보충 설명한다.
2. **같은 개념을 다른 상황으로** 즉시 재질문한다.
   방금 설명을 그대로 되뇌면 못 맞히도록 각도를 바꾼다.
   예: 복합 인덱스 컬럼 순서를 `WHERE b=1`로 물었다면 재질문은 `ORDER BY b`로.
3. 재질문에서 맞히면 `해결`, 또 틀리면 개념을 끝까지 설명하고 `미해결`로 남긴다.

재질문은 문항 수에 포함하지 않는다. 5문항이면 신규 문항이 5개다.

## 기록

경로: `~/.claude/end-test/YYYY-MM-DD.md` (하루 한 파일, 세션별로 이어붙임)

✗가 난 항목만 기록한다. 항목당 다음을 남긴다.

- 주제
- 세션에서 무엇을 하다 나왔는가
- 무엇을 몰랐는가 (오개념이면 어떤 오개념인지)
- 보충 설명 요지
- 해결 / 미해결

기록 예:

```markdown
## PostgreSQL 복합 인덱스 컬럼 순서
- 상태: 미해결
- 맥락: Cofathon 백엔드 조회 쿼리 튜닝 중 (a, b) 인덱스 추가
- 무엇을 몰랐는가: 선행 컬럼 조건 없이 후행 컬럼만 쓰면 인덱스를
  못 탄다는 점. B-tree가 선행 컬럼 기준으로 정렬된다는 구조와
  연결이 안 됨.
- 보충: 복합 인덱스는 (a, b) 순으로 정렬된 하나의 키다. a가 고정되지
  않으면 b는 전체에 흩어져 있어 범위 탐색이 성립하지 않는다.
```

이 파일은 학습 로그이지 재출제 대기열이 아니다. 다음 세션의 출제에
자동으로 반영하지 않는다. ✗는 그 자리에서 재질문으로 처리했기 때문이다.

## 마무리 출력

문항이 끝나면 요약한다.

- 판정 분포 (○ n · △ n · ✗ n)
- △와 ✗가 난 주제 목록 한 줄씩
- 기록 파일 경로

점수나 등급은 매기지 않는다. 숫자는 학습 신호를 가린다.

개발과 사용이 같은 파일을 본다.

## 검증

스킬이므로 자동 테스트 대상이 아니다. 아래를 수동으로 확인한다.

1. 실제 작업 세션 뒤 `/end-test`를 돌려 문항이 그 세션 내용에서 나오는지
2. 네 축이 고르게 나오는지, "그냥 넘어간 지점"이 실제로 짚이는지
3. 일부러 얕게 답해서 △가 나오는지 (○로 후하게 채점되지 않는지)
4. 일부러 틀려서 재질문이 각도를 바꿔 나오는지
5. 기록 파일이 형식대로 쓰이는지
6. `/end-test 3` 이 3문항으로 도는지

3번이 가장 중요하다. 채점이 후하면 도구 전체가 무의미해진다.
